# SLRResearchAI course summary

The workspace contains eight documented practicals, **TD01 through TD08**. They start with a single LLM call to propose research questions and end with a five-role orchestration exercise that evaluates and revises a synthesis using supplied artifacts. The recurring lesson is that prompts propose outputs, while Python controls validation, permissions, evidence, budgets, routing, and escalation.

Those boundaries matter when assessing how much of the sequence has been executed together.

## Practical exercises

### TD01 — Prompting and decoding

**What we learned.** A system prompt defines the model's role, scope, language and guardrails. A user prompt supplies the task, context, current topic, constraints and output format. Zero-shot means the prompt gives instructions without worked examples. The course asks for three to five open, distinct questions in French, numbered as research questions and returned as plain text. The companion note introduces LangChain's common `Runnable.invoke()` interface and the chat roles `SystemMessage`, `HumanMessage` and `AIMessage`. See [ENONCE_TD01.md, §§1–4](SLRResearchAI-TD01/ENONCE_TD01.md#L3) and [COMPRENDRE_INVOKE_LANGCHAIN.md, §§2–9](SLRResearchAI-TD01/COMPRENDRE_INVOKE_LANGCHAIN.md#L17).

**Implementation and stack.**

1. `build_system_prompt()` and `build_user_prompt()` construct the messages. The latter rejects a blank topic before any call.
2. `generate_questions()` makes one call through `model.invoke(messages)`, trims the text and returns `FreeTextQuestions` with the provider, prompts, latency, and token counts or stop reason when supplied.
3. `resolve_decoding()` translates `greedy` and `sampling` into parameters. In this implementation, greedy requests temperature 0 and top-p 1, with top-k 1 passed to Ollama. The code describes the Groq configuration as an approximation. Temperature controls how strongly the distribution favors high-scoring tokens, top-p restricts the cumulative probability mass considered, and Ollama's top-k limits the number of token candidates. The output-token cap bounds response length.
4. `main.py` holds the experimental settings. Streamlit reads them and shows a real-provider mode and an explicitly prepared demonstration. Python dataclasses hold settings and results. LangChain Core and its Ollama/Groq adapters handle model calls, `python-dotenv` loads provider configuration, and pytest uses a fake model to check the call and metadata. See [research_questions.py, lines 20–97](SLRResearchAI-TD01/slrresearch/research_questions.py#L20), [config.py, lines 27–64](SLRResearchAI-TD01/slrresearch/config.py#L27), [main.py](SLRResearchAI-TD01/main.py), [streamlit_app.py, lines 21–90](SLRResearchAI-TD01/streamlit_app.py#L21) and [test_td01.py](SLRResearchAI-TD01/tests/test_td01.py).

**Experiment, limits and reuse.** The exercise asks for three runs per greedy/sampling configuration, then three runs per temperature at 0.2 and 0.8 with sampling, top-p 0.9 and a 400-token cap held fixed. The first comparison changes a strategy, while the second isolates temperature. The assignment states `4 passed`. The checked-out suite contains nine passing cases. The tests measure assembly and configuration. No completed repeated-run table was found. Reuse the narrow one-call interface, provider abstraction and metadata collection for drafting RQs, with a separate decision about scientific suitability. See [ENONCE_TD01.md, §§5–6](SLRResearchAI-TD01/ENONCE_TD01.md#L123).

### TD02 — From free text to a controlled workflow

**What we learned.** The assignment presents conforming and nonconforming outputs for both zero-shot and few-shot. Few-shot shows two completed examples. Every variant is judged by the same rules. The raw-text check answers whether the model wrote parseable lines. The Pydantic contract answers whether the extracted fields have the required structure. See [ENONCE_TD02.md, §§1–4 and Parts A–D](SLRResearchAI-TD02/ENONCE_TD02.md#L3) and [COMPTE_RENDU_TD02.md, synthesis answers](SLRResearchAI-TD02/COMPTE_RENDU_TD02.md#L9).

**Implementation and stack.**

1. `extract_non_empty_lines()` strips whitespace. `parse_rq_line()` uses a full-line regex. Python checks exactly `RQ1`, `RQ2`, `RQ3` in order and uses a set to detect duplicate wording. This is deliberately stricter than TD01's prompt.
2. `validate_questions()` converts the records into `ResearchQuestion` Pydantic models with an identifier pattern and a minimum question length.
3. `run_controlled_workflow()` returns `accepted` on the first success. On a validation error it sends the original text, precise error, expected form and an example to a one-call repair prompt. It reuses the same validators and returns `repaired` or `human_required`. Preserving the question's meaning is a prompt instruction.
4. `build_question_pipeline()` uses LangChain Expression Language (LCEL). `RunnableLambda` wraps text validation, object validation and query construction, joined with `|`. Invoking that chain executes deterministic Python functions. `build_queries()` uses three task phrases and three technology phrases from `SEARCH_CONCEPTS`. It joins the nine quoted pairs with `OR`, with `AND` inside each pair, and returns the same expression under the pedagogical keys `scholar`, `ieee` and `acm`. The validated RQs gate this step. The query terms are the supplied constants.
5. The CLI compares zero-shot and few-shot. Streamlit shows the controlled branches and the last result in session state. The TD03 continuity guide shows the optional JSON export and key mapping, which the current TD02 entry points do not perform. The exercise uses Python regex, sets, Pydantic, LangChain Core and its existing provider adapters, Streamlit and pytest. See [search_plan.py, lines 8–230](SLRResearchAI-TD02/slrresearch/search_plan.py#L8), [main.py, lines 20–51](SLRResearchAI-TD02/main.py#L20), [streamlit_app.py, lines 166–195](SLRResearchAI-TD02/streamlit_app.py#L166), [test_td02.py](SLRResearchAI-TD02/tests/test_td02.py) and [CONTINUITE_REELLE_TD02.md, export instructions](SLRResearchAI-TD03/CONTINUITE_REELLE_TD02.md#L16).

**Limits and reuse.** Duplicate wording detection is exact after trimming, and validation checks form rather than coverage or scientific novelty. Keep the strict interface and bounded repair for a later review protocol, with topic-specific concepts and database-specific query syntax treated as separate work. Use the same validator when measuring the effect of examples or repair.

### TD03 — From tool workflow to controlled ReAct

**What we learned.** Tool use means software calls an external capability. In Version A, Python fixes the sequence of those calls. In Version B, a decision policy sees the current state and chooses the next action after each observation. ReAct is this interleaving of decision, action and observation. A deterministic policy can exhibit this behavior. The LLM policy changes who proposes the action. See [ENONCE_TD03.md, §§1–4 and TODO 8](SLRResearchAI-TD03/ENONCE_TD03.md#L3).

**Implementation and stack.**

1. `load_search_plan()` reads `artifacts/search_plan.json` and requires three nonempty queries keyed by `openalex`, `crossref` and `semantic_scholar`. The shipped plan identifies itself as `pedagogical_seed`.
2. A policy proposes `search` or `finish`. `AgentAction` checks arguments and a search limit between 1 and 20. The registry separately authorizes tool names. `LLMDecisionPolicy` exposes a compact state projection and the allowlist in its prompt, calls the model once for that decision, then parses a JSON object from its text. This is an application-managed tool call, with no native tool binding in this path.
3. `execute_authorized_action()` dispatches through `SearchTool`. It turns supported outcomes into `Observation` values, including success, empty, HTTP 429, other HTTP or network errors, and denied tools. The demo uses a local paper catalog and can simulate a 429. The real registry invokes OpenAlex, Crossref and Semantic Scholar through HTTPX and maps their metadata into `PaperRecord`.
4. `update_state()` records actions, observations, errors and paper records, using the lowercased DOI or title as a deduplication key. `run_react_agent()` validates proposals, records schema-invalid actions, and stops on `agent_finish`, `target_reached` or `max_steps`. `finish` makes no tool call. The demo policy can switch from OpenAlex to Crossref after a recoverable failure, then finish. Version A runs the configured query sequence regardless of that choice.
5. `main.py` and Streamlit expose the traces. Tests use scripted policies, example artifacts and mocked HTTP responses. The exercise uses Python, Pydantic, HTTPX, LangChain/provider adapters, JSON, Streamlit and pytest. See [handoff.py](SLRResearchAI-TD03/slrresearch/handoff.py), [contracts.py, lines 18–87](SLRResearchAI-TD03/slrresearch/contracts.py#L18), [tools.py](SLRResearchAI-TD03/slrresearch/tools.py), [real_tools.py](SLRResearchAI-TD03/slrresearch/real_tools.py), [runtime.py](SLRResearchAI-TD03/slrresearch/runtime.py), [policies.py](SLRResearchAI-TD03/slrresearch/policies.py), [demo.py](SLRResearchAI-TD03/slrresearch/demo.py), [workflow.py](SLRResearchAI-TD03/slrresearch/workflow.py), [react_agent.py](SLRResearchAI-TD03/slrresearch/react_agent.py) and [test_td03.py](SLRResearchAI-TD03/tests/test_td03.py).

**Limits and reuse.** Comparing orders and stop reasons illustrates control flow, not search exhaustiveness. A malformed JSON decision can fail before the schema-validation handler because `decide()` is called outside that handler. The DOI-or-title key keeps the first record with a matching key and does not unify DOI strings expressed differently. TD03's OpenAlex adapter leaves abstracts blank. The TD04 copy adds abstract reconstruction and cleanup. Reuse the registry, normalized records, trace and fixed baseline. The assignment's suggested minimum multi-source coverage rule is a discussion example, separate from the implemented stopping rules. See [ENONCE_TD03.md, lines 1016–1049](SLRResearchAI-TD03/ENONCE_TD03.md#L1016), [TD03 tools.py, line 64](SLRResearchAI-TD03/slrresearch/tools.py#L64), [TD04 tools.py, lines 14–26](SLRResearchAI-TD04/slrresearch/tools.py#L14) and [COMPTE_RENDU_TD03.md, questions 12–17](SLRResearchAI-TD03/COMPTE_RENDU_TD03.md#L126).

### TD04 — Controlled title and abstract screening

**What we learned.** A **criterion** is part of the review protocol. An **indicator** is an observed signal from the record. A **verdict** applies the policy to those observations. Screening operates on the deduplicated title and abstract before full-text eligibility. An `include` at this point advances a paper to the next stage. Missing abstracts, contradictory signals, and model disagreement motivate abstention and human review. See [ENONCE_TD04.md, §§1–3 and §6](SLRResearchAI-TD04/ENONCE_TD04.md#L3).

**Implementation and stack.**

1. `load_search_artifact()` validates schema version, TD03 origin, search metadata and paper records. The supplied main artifact records OpenAlex and Crossref success and a Semantic Scholar 429, with 16 unique papers, 10 with abstracts according to the handout. Tests also use a separate five-paper fixture. Treat the saved run as historical evidence.
2. **A, rule screening.** `observe_indicators()` lowercases and joins title and abstract, checks inclusion and exclusion phrases, and flags missing data or conflict. The preliminary policy gives exclusion priority over inclusion, otherwise returning `uncertain`. The human queue captures uncertainty, scores below the configured threshold, conflicts and missing information. Scores such as 0.95, 0.90 and 0.45 are rule values.
3. **B, LLM screening.** LangChain's `with_structured_output(LLMScreeningDecision)` supplies a Pydantic schema and one call per record. The application restores the input paper ID. The quote must appear in the title or abstract after normalization, except that an empty quote is allowed for `uncertain`. An unverifiable quote becomes an uncertain, zero-confidence recommendation flagged for review. Passing this check establishes lexical anchoring.
4. **C, cooperation and human arbitration.** `compare_decisions()` aligns A and B by paper in the interface, compares the original automated outputs and sends a disagreement or either review flag to a human. The Streamlit form requires a reason and allows `uncertain` to remain pending. Human decisions are stored in session state. The downloadable input artifact and on-screen outputs are present. The final TD05 screening artifact is supplied separately.
5. Python dataclasses represent rule outputs, Pydantic validates artifacts and model decisions, LangChain provides the model adapter, and Streamlit supplies the comparison and review interface. Tests cover the artifact contract, the rule policy, grounding failure and disagreement. See [artifacts.py, lines 18–41](SLRResearchAI-TD04/slrresearch/artifacts.py#L18), [screening_agent.py, lines 23–152](SLRResearchAI-TD04/slrresearch/screening_agent.py#L23), [llm_screening_agent.py, lines 51–176](SLRResearchAI-TD04/slrresearch/llm_screening_agent.py#L51), [streamlit_app.py, review and outputs](SLRResearchAI-TD04/streamlit_app.py#L397), [search_results.json](SLRResearchAI-TD04/artifacts/search_results.json), [test_td04.py](SLRResearchAI-TD04/tests/test_td04.py) and [test_td04_llm.py](SLRResearchAI-TD04/tests/test_td04_llm.py).

**Limits and reuse.** Substring matches can confuse unrelated uses of “screening”. A quote can be present and still fail to support the verdict. The rule scores and LLM confidence reports have no calibration evidence. Reuse the independent screening paths, visible disagreements and human reasons as part of auditable eligibility decisions. Persistent adjudication and a full-text eligibility workflow remain integration work. See [ENONCE_TD04.md, TODOs 9–10 and §§7–9](SLRResearchAI-TD04/ENONCE_TD04.md#L457) and [COMPTE_RENDU_TD04.md, questions 7–17](SLRResearchAI-TD04/COMPTE_RENDU_TD04.md#L244).


### TD05 — Classical RAG with traceable evidence

**What we learned.** Retrieval-augmented generation gives a model selected passages at answer time. The course separates document preparation, chunking, ranking, context assembly, extraction and verification. TF-IDF scores token overlap while giving rarer words more weight. Embeddings encode texts as vectors, so a semantic search can retrieve a relevant passage despite different wording. Both paths rank with cosine similarity and keep the highest-scoring `k` chunks. See [ENONCE_TD05_RAG.md, §§1–3 and TODOs 1–10](SLRResearchAI-TD05/ENONCE_TD05_RAG.md#L3).

**Implementation and stack.**

1. `load_rag_handoff()` validates the search results, screening decisions and document manifest. It joins them and the extracted-page map by `paper_id` and document key, selecting records present in search, included in decisions and marked downloaded with extracted pages. The furnished experimental corpus has three records, two selected documents, and four chunks under the recorded setup.
2. The provided `extract_pdf_pages()` uses `pypdf.PdfReader` and preserves page order. The classroom comparison uses pre-extracted text. `chunk_pages()` cuts each page by character count, with optional overlap and a validated positive stride `size - overlap`. Each chunk records a `paper_id`, a stable chunk ID, page and text. Image-only PDFs require OCR outside this implementation.
3. `lexical_retrieve()` builds sparse TF-IDF vectors with Python counters. `semantic_retrieve()` embeds the query and chunks and computes dense cosine similarity in memory. There is no external vector store. The optional real embedding mode uses `OllamaEmbeddings` with default `nomic-embed-text`. `retrieval_metrics()` computes precision from relevant retrieved IDs divided by the number returned, and recall from relevant retrieved IDs divided by the annotated relevant set size. Both use the same reference IDs in the comparison.
4. `run_rag()` passes only the selected passages, tagged by paper, chunk and page, to the extractor. A Pydantic `ProposedEvidence` captures the answer, supporting quote and provenance. `verify_evidence()` looks up the quoted chunk within that top-k context, checks page and paper ID and checks the quote after whitespace/case normalization. Exact matches with aligned provenance are `verified`. Similar text or a matching quote with inconsistent provenance can require `human_review`. A missing chunk or unmatched quote can be `rejected`. The UI serializes the result, including its status, as `verified_evidence.json`.
5. The CLI demonstrates corpus loading, chunking and lexical ranking. Streamlit supports the paired comparison and extraction. Python provides TF-IDF, cosine calculation and `SequenceMatcher`. Pydantic provides schemas, LangChain handles structured extraction and the optional embeddings, pypdf handles PDF text, and pytest covers ranking, contracts, quote verification and artifact transfer. See [rag_artifacts.py, lines 62–114](SLRResearchAI-TD05/slrresearch/rag_artifacts.py#L62), [pdf_loader.py](SLRResearchAI-TD05/slrresearch/pdf_loader.py), [rag_pipeline.py, lines 12–168](SLRResearchAI-TD05/slrresearch/rag_pipeline.py#L12), [config.py](SLRResearchAI-TD05/slrresearch/config.py), [streamlit_app.py](SLRResearchAI-TD05/streamlit_app.py), [test_td05.py](SLRResearchAI-TD05/tests/test_td05.py) and [test_artifact_chain.py](SLRResearchAI-TD05/tests/test_artifact_chain.py).

**Results, limits and reuse.** The saved same-corpus comparison uses `k=2`. For Q1 and Q3, both retrievers achieve precision 0.50 and recall 1.00. For Q2, lexical scores 0 on both and the controlled semantic path scores 0.50 and 1.00. The controlled vectors use the correct labels to manufacture the intended rank, testing the pipeline and metrics. The report describes controlled Streamlit AppTest coverage and leaves real embeddings, generation and PDF extraction unverified. Reuse the evidence contract, labeled baseline and provenance checks. To evaluate a real retriever, keep annotations independent of ranking. BM25 is a named reading topic in the README. The shipped baseline is TF-IDF, and the referenced lexical retrieval guide is missing. See [COMPTE_RENDU_TD05.md, §§2–7](SLRResearchAI-TD05/COMPTE_RENDU_TD05.md#L30), [rag_comparison.json](SLRResearchAI-TD05/artifacts/rag_comparison.json), [verified_evidence.json](SLRResearchAI-TD05/artifacts/verified_evidence.json) and [README.md, lines 13–15](SLRResearchAI-TD05/README.md#L13).

### TD06 — Adaptive retrieval and bounded working memory

**What we learned.** An evidence facet is a particular part of a question that the retrieved material needs to address. A retrieval agent can check which facets are missing and choose another query or retriever, stop with evidence, or abstain. The exercise makes the cost of adaptation visible by comparing an extra retrieval against a fixed baseline. See [ENONCE_TD06.md, §§1–4 and TODOs 1–8](SLRResearchAI-TD06/ENONCE_TD06.md#L3).

**Implementation and stack.**

1. The CLI and UI reuse the TD05 handoff, chunker and retrievers. `agentic_rag_cases.json` specifies three questions, facet keywords, query hints and annotated relevant chunk IDs. The TD06 extracted corpus has five chunks under the shipped protocol, compared with four in the recorded TD05 experiment.
2. `AdaptiveRAGState` starts with all required facets missing. `controlled_decider()` first requests lexical retrieval. `execute_retrieval_action()` dispatches a typed `RetrievalAction` through the permitted lexical/semantic tools. After each retrieval, `merge_candidates()` retains the best score per chunk, sorts the results and enforces a memory limit. `evaluate_facets()` searches the merged text for known keywords. The update stores covered and missing facets, iteration and retrieval counts, and one trace entry per retrieval.
3. The rule policy finishes when all facets are covered, targets the missing facets with a semantic query when another cycle is available, or abstains when evidence remains insufficient. `run_adaptive_retrieval()` enforces the tool-call cap and distinguishes `completed`, `abstained` and `budget_exhausted`. `finalize_agentic_evidence()` only calls the extractor for a completed run with selected chunks, then reuses TD05 verification.
4. The optional LLM policy uses LangChain structured output with `RetrievalAction`, limiting the available tool names and passing facet-specific hints. The Streamlit wrapper starts with the lexical baseline and can fall back to the controlled policy for invalid or unsuitable model decisions. The generic loop trusts a supplied decider's `finish` action, so a future caller needs to preserve the coverage guard when reusing it.
5. `compare_baseline_and_agentic()` applies the same relevant IDs and reports precision, recall, facet coverage, status and extra retrieval calls. The implementation uses Python callables and collections, Pydantic state/action models, the TD05 tooling, LangChain adapters, Streamlit and pytest. Tests cover allowlisting, merge limits, trace updates, structured model returns, integration with all three cases, voluntary abstention and budget exhaustion. See [agentic_rag.py, lines 21–261](SLRResearchAI-TD06/slrresearch/agentic_rag.py#L21), [agentic_rag_models.py](SLRResearchAI-TD06/slrresearch/agentic_rag_models.py), [agentic_rag_runtime.py](SLRResearchAI-TD06/slrresearch/agentic_rag_runtime.py), [streamlit_app.py, guarded decision path](SLRResearchAI-TD06/streamlit_app.py#L145), [test_td06.py](SLRResearchAI-TD06/tests/test_td06.py) and [test_td06_integration.py](SLRResearchAI-TD06/tests/test_td06_integration.py).

**Results, limits and reuse.** The recorded two-cycle protocol raises recall from 0 to 1 on Q1 and Q2 at the cost of one extra retrieval each. Q3 already reaches recall 1 in one lexical cycle. At budget one, Q1 and Q2 exhaust the budget, while Q3 completes on the delivered corpus. The brief's suggestion that Q3 can illustrate abstention depends on the corpus and settings. The controlled semantic vectors use the relevance annotations, facet coverage is based on substring matches, and the implementation compares scores from different retrievers directly. These are teaching simplifications. Reuse the state, observation-driven decision loop, explicit abstention, and cost comparison for targeted evidence gaps. See [COMPTE_RENDU_TD06.md, §§3–7](SLRResearchAI-TD06/COMPTE_RENDU_TD06.md#L65), [agentic_rag_cases.json](SLRResearchAI-TD06/artifacts/agentic_rag_cases.json) and [td06_ui_validation.json](SLRResearchAI-TD06/artifacts/td06_ui_validation.json).

### TD07 — Plan-and-Execute on a comparative mini-corpus

**What we learned.** Plan-and-Execute first constructs a multi-step plan with dependencies and assigned evidence. A validator and executor check it before producing each section. A retry repeats the same step. Replanning revises the remaining work in response to an observed failure, then revalidates it. The supplied mini-corpus represents four primary studies, eight evidence items and three RQs. Some evidence items come from the same study. The deliverable is a pedagogical synthesis note. See [ENONCE_TD07.md, §§1–4 and 6–13](SLRResearchAI-TD07/ENONCE_TD07.md#L3) and [td06_evidence.json](SLRResearchAI-TD07/artifacts/td06_evidence.json).

**Implementation and stack.**

1. `load_td06_handoff()` reads the prepared mini-corpus into `EvidenceItem` records with source, question, finding and facets. `PlanCandidate` contains `PlanStep` records with objectives, dependencies, allowed evidence IDs, required facets and an execution mode.
2. The optional LangChain planner uses one structured call for **Direct**. **Structured CoT** uses two calls, first producing an observable `PlanningAnalysis` with ordering, justifications and risks, then a plan. The **ToT exercise** makes three independent plan proposals, one each for organization by RQ, strategy or risk. Python filters invalid candidates and selects by RQ coverage, dependency consistency and section completeness. The protocols enforce a strategy-specific RQ order and dependency pattern for the experiment. The comparison therefore includes those deliberate structural differences. The supplied fixture planner can run all three with zero live calls.
3. `validate_plan()` rejects duplicate step IDs or RQs, unknown evidence, self-dependency, forward or unknown dependencies and missing required RQs. `evaluate_plan()` records validity, RQ coverage, section completeness and dependency consistency. Dependencies must point backward in the given order, which also prevents cycles in accepted plans.
4. `execute_step()` checks completed dependencies and evidence permissions, measures facet coverage and returns a typed result with paper citations. `observe_step()` reports success, coverage, citation validity and remaining action budget. `run_classic()` retries the unchanged step within its budget, then abstains if it cannot finish. `run_with_replanning()` permits bounded changes, checks that completed step IDs remain and reruns plan validation. The provided replanner replaces an unsupported prospective-validation demand with explicit limitation wording and preserves available supporting evidence.
5. `build_report_markdown()` assembles executed sections with paper, page, evidence ID and limitations. Its synthesis is based on the supplied findings and deterministic assembly. The CLI and Streamlit use the planning/report code. Pydantic covers plans, evidence, step results and events, LangChain handles optional structured planning, and pytest exercises the planner adapter with fake outputs plus plan and runtime invariants. See [planning_models.py](SLRResearchAI-TD07/slrresearch/planning_models.py), [plan_and_execute.py, validation](SLRResearchAI-TD07/slrresearch/plan_and_execute.py#L104), [execution and replanning](SLRResearchAI-TD07/slrresearch/plan_and_execute.py#L185), [LLM planner](SLRResearchAI-TD07/slrresearch/plan_and_execute.py#L337), [td07_runtime.py](SLRResearchAI-TD07/slrresearch/td07_runtime.py), [test_td07.py](SLRResearchAI-TD07/tests/test_td07.py) and [test_td07_regressions.py](SLRResearchAI-TD07/tests/test_td07_regressions.py).

**Results, limits and reuse.** The saved same-executor comparison produces two sections with Direct and three each with the supplied CoT and ToT plans. With the same Direct plan, fixed retry abstains at two sections, while one replan produces three sections by documenting the evidence gap. Both take four execution actions in that comparison. The saved run has zero actual LLM calls. The fixed candidate exercise does not establish the superiority of a planning method or provide a full tree-search system. Use the completed TD07 validator, executor and cited note builder as reuse candidates. The planner copy in TD08 has disabled checks and `None` placeholders in execution and LLM planning. See [COMPTE_RENDU_TD07.md, §§4–8](SLRResearchAI-TD07/COMPTE_RENDU_TD07.md#L103), [td07_execution.json](SLRResearchAI-TD07/artifacts/td07_execution.json), [td07_note_synthese.md](SLRResearchAI-TD07/artifacts/td07_note_synthese.md) and [TD08 plan_and_execute.py, unfinished validation](SLRResearchAI-TD08/slrresearch/plan_and_execute.py#L95), [execution](SLRResearchAI-TD08/slrresearch/plan_and_execute.py#L179) and [planning](SLRResearchAI-TD08/slrresearch/plan_and_execute.py#L332).

### TD08 — QualityAgent and multi-agent orchestration

**What we learned.** A structured synthesis can be checked one atomic claim at a time. Citation existence, evidence support and coverage of the review questions measure different things. A typed handoff gives another role its objective, artifact, authorized evidence IDs, status and budget. A supervisor can route quality feedback to the responsible role. See [ENONCE_TD08.md, objective and eight TODOs](SLRResearchAI-TD08/ENONCE_TD08.md#L3).

**Implementation and stack.**

1. `parse_claims()` validates each `Claim`. `evaluate_rules()` measures the fraction of required RQs with sections, the fraction of claims with known nonempty evidence IDs, and the fraction of claims whose cited text or finding shares at least two qualifying tokens with the claim. The last value is called `faithfulness` in the code and measures lexical overlap. The score is the mean of the three. Acceptance requires the threshold and no rule feedback. Unsupported claims route to RAG, and other repairable issues route to Writing.
2. `build_llm_judge()` makes one structured LangChain call using a Pydantic `QualityJudgeDecision`. It merges feedback, takes the lower score and preserves the stricter verdict, leaving rule objections in force. `run_quality_loop()` evaluates, sends feedback to a writer, and re-evaluates within a revision cap. Acceptance, direct escalation, and exhaustion are explicit outcomes.
3. `validate_handoff()` checks the allowed source-to-target transition, presence of evidence IDs in `SharedState`, and a nonnegative budget. The full fixed pipeline runs Search → Screening → RAG → Writing → Quality once, then finishes or escalates. The full supervisor starts with the same chain. It can route an evidence problem Quality → RAG → Writing → Quality, or a writing problem Quality → Writing → Quality. Human routing and budget exhaustion are terminal outcomes. Both maintain shared state and visible execution traces. The shorter `pipeline_run()` and `supervisor_run()` functions are earlier examples.
4. The provided workers read saved search, screening and RAG artifacts. The writer returns the supplied initial draft on its first call and the supplied correction on later calls. The loop's standalone writer is also a fixture. The same orchestration functions accept injected workers and an evaluator, which enables controlled unit and regression tests. Streamlit shows claim changes and handoffs and offers a configurable judge. The CLI generates a JSON comparison and Markdown note. This uses Python, Pydantic, optional LangChain provider adapters, Streamlit with DOT diagrams, JSON and pytest. See [quality_models.py](SLRResearchAI-TD08/slrresearch/quality_models.py), [quality_agent.py, lines 12–143](SLRResearchAI-TD08/slrresearch/quality_agent.py#L12), [orchestrator.py, lines 14–177](SLRResearchAI-TD08/slrresearch/orchestrator.py#L14), [td08_runtime.py, artifact workers](SLRResearchAI-TD08/slrresearch/td08_runtime.py#L24), [main.py, run_demo](SLRResearchAI-TD08/main.py#L12), [streamlit_app.py](SLRResearchAI-TD08/streamlit_app.py), [test_td08.py](SLRResearchAI-TD08/tests/test_td08.py) and [test_td08_regressions.py](SLRResearchAI-TD08/tests/test_td08_regressions.py).
